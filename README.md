# AI Quant Bot v21.0 — State Persistence Fix (Critical)

این نسخه ریشهٔ واقعی مشکل «۴ گزارش روزانه در یک روز» را پیدا و رفع کرد — و ریشه، عمیق‌تر
از گزارش روزانه بود: **از روز نصب، هیچ‌وقت هیچ state ای واقعاً در مخزن ذخیره نشده بود.**

## 🐛 باگ بحرانی: `git add` به‌طور کامل شکست می‌خورد

مرحلهٔ «Save state & history» در Workflow این دستور را اجرا می‌کرد:
```bash
git add state/state.json.enc state/state.json.enc.bak data/history.csv
```

وقتی حتی **یکی** از این سه فایل هنوز وجود نداشته باشد (مثلاً `data/history.csv` که تا
اولین بسته‌شدن یک معامله اصلاً ساخته نمی‌شود، یا `state.json.enc.bak` که تا دومین ذخیره
ساخته نمی‌شود)، دستور `git add` با خطای `pathspec did not match any files` **کاملاً و
به‌طور کلی شکست می‌خورد — و هیچ‌کدام از فایل‌ها، حتی آن‌هایی که وجود داشتند و واقعاً
تغییر کرده بودند، stage نمی‌شدند.** نتیجه: `git diff --cached --quiet` هیچ تغییری
نمی‌دید، پیام «No state changes to commit» چاپ می‌شد، و **هیچ‌چیز هرگز commit نمی‌شد.**

با تست مستقیم با خود `git` (نه فرض یا حدس) این رفتار عیناً بازتولید و تأیید شد.

### چرا این باعث می‌شد گزارش روزانه تکرار شود؟

چون `state.json.enc` هرگز واقعاً commit نمی‌شد، **هر اجرای جدید GitHub Actions با یک
مخزن کاملاً بدون state شروع می‌کرد** (چون `checkout` همیشه آخرین نسخهٔ commit‌شده را
می‌آورد، و آخرین نسخهٔ commit‌شده هرگز به‌روز نشده بود). یعنی `last_report_date` همیشه
خالی بود، پس ربات هر بار فکر می‌کرد «اولین اجرای امروز» است و دوباره گزارش می‌فرستاد.
همین مشکل روی هشدار SL، Cooldown، Circuit Breaker و آمار عملکرد هم اثر می‌گذاشت —
چون هیچ‌کدام از این‌ها هم هیچ‌وقت واقعاً حفظ نمی‌شدند.

## ✅ رفع باگ

به‌جای یک دستور `git add` با چند مسیر، حالا هر فایل جداگانه و فقط در صورت وجود، اضافه
می‌شود:
```bash
for f in state/state.json.enc state/state.json.enc.bak data/history.csv; do
  if [ -f "$f" ]; then
    git add "$f"
  fi
done
```

### تأیید با شبیه‌سازی کامل دو اجرای پشت‌سرهم

یک مخزن Git واقعی ساختم و دقیقاً همان الگوی شما (بازار آرام، بدون سیگنال) را برای دو
«اجرای» جداگانه شبیه‌سازی کردم:
- **اجرای ۱:** «هیچ فایل state موجودی پیدا نشد؛ با state پیش‌فرض تازه شروع می‌شود» →
  commit موفق.
- **اجرای ۲ (چک‌اوت کاملاً تازه، مثل یک اجرای واقعی جدید):** «**state موجود با موفقیت
  بارگذاری شد**» → گزارش روزانه این‌بار درست ارسال نشد (چون تاریخ را به‌خاطر داشت) →
  commit دوم هم موفق.

این دقیقاً رفتاری است که باید از اول وجود می‌داشت.

## 🔍 بهبود تشخیصی اضافه‌شده

از این پس، هر اجرا در لاگ **همیشه** (نه فقط در خطا) دقیقاً می‌گوید state از کجا آمد:
- `state موجود با موفقیت بارگذاری شد` — همه‌چیز عادی است.
- `هیچ فایل state موجودی پیدا نشد؛ ...` — طبیعی فقط در اولین اجرا؛ اگر همیشه این را
  دیدید، یعنی هنوز مشکلی در ذخیره‌سازی هست.
- `state از نسخهٔ backup بازیابی شد` — یعنی فایل اصلی مشکل داشت اما بازیابی موفق بود.

مرحلهٔ «Save state» هم حالا خروجی `git status --short` را چاپ می‌کند تا همیشه شفاف
ببینید دقیقاً چه فایلی commit شده.

## ⚠️ توصیهٔ من: یک نصب تازهٔ کامل (نه فقط این یک فایل)

با توجه به اینکه در طول این پروژه حدود ۲۰ بار فایل‌ها را از گوشی و به‌صورت دستی
جایگزین کرده‌اید، احتمال باقی‌ماندن یک فایل قدیمی/ناقص جایی وجود دارد که ممکن است
باگ‌های دیگری پنهان کرده باشد. برای اطمینان ۱۰۰٪، پیشنهاد می‌کنم:

1. تمام فایل‌های فعلی مخزن را حذف کنید (یا یک مخزن Private جدید بسازید).
2. تمام فایل‌های این نسخه (v21) را از صفر آپلود کنید.
3. Secrets را دوباره وارد نکنید — همان‌ها که الان دارید کار می‌کنند، فقط دست نزنید.
4. یک‌بار **Run workflow** دستی بزنید و مطمئن شوید در لاگ `state موجود با موفقیت
   بارگذاری شد` را در اجرای دوم می‌بینید (اجرای اول طبیعتاً «هیچ فایلی پیدا نشد» می‌گوید).
